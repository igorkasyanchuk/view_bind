view_bind · як це влаштовано

Гем, який не рендерить швидше — він менше готується

Кожен виклик render у Rails виконує приблизно однакову підготовку, скільки б не важив сам партіал. view_bind робить цю підготовку один раз на місце виклику і далі викликає скомпільований метод шаблону напряму.

render partial: 5.75 мкс bind_render 1.00 мкс на сторінці 2 662 → 1 виклик рендеру об’єктів 3.30× менше

01Куди йде час у звичайному render

Партіал у Rails — це вже скомпільований Ruby-метод. Але щоб дійти до нього, render щоразу проходить увесь шлях: збирає хеш опцій, створює новий PartialRenderer, витягує details, шукає шаблон, кидає нотифікацію, робить окремий OutputBuffer і копіює рядок із нього в батьківський буфер.

02Що робить bind_render

Rails уже скомпілював кожен партіал у метод на спільному модулі. Гем один раз знаходить цей метод, кладе UnboundMethod у кеш і далі викликає його через bind_call — з тим самим обліком, що робить ActionView::Base#_run.

lib/view_bind/helper.rb
def bind_render(path, **locals, &block)
  raise ArgumentError, "bind_render does not support a block" if block

  render_bound(ViewBind.bound_for_locals(self, path, locals), locals)
  nil
end

# повторює ActionView::Base#_run: скомпільований метод очікує, що буфер і облік
# шаблонів на місці, а @virtual_path він виставляє собі сам
def bind_run(bound, locals, buffer)
  previous_buffer, previous_path, previous_template = @output_buffer, @virtual_path, @current_template
  @current_template = bound.template
  @output_buffer    = buffer
  bound.unbound_method.bind_call(self, locals, buffer)
  nil
rescue StandardError => e
  bound.template.send(:handle_render_error, self, e)   # та сама обгортка, що в Rails
ensure
  @output_buffer, @virtual_path, @current_template = previous_buffer, previous_path, previous_template
end

Чому це не «хак з приватним API навмання»

Гем справді використовує три :nodoc: методи ActionView — compile!, method_name, handle_render_error. Якщо якийсь із них зникне в майбутньому Rails, fast_path_available? це побачить і все піде через звичайний Template#render: втратиться прискорення, а не додаток.

03Кеш біндінгів: три рівні

Щоб не шукати шаблон щоразу, знайдений Bound лежить у вкладених хешах. Попадання не створює жодного об’єкта: імена locals порівнюються з хешем на місці, без locals.keys.

04Колекції: облік винесено з циклу

У циклі всі елементи рендерять один і той самий шаблон. Тож bind_render_each зберігає й відновлює ivar-и view один раз на всю колекцію, а не на кожен елемент, і перевикористовує один хеш locals — так само, як робить власний CollectionRenderer у Rails.

05Що навмисно не ламається

Партіал лишається звичайним скомпільованим шаблоном Rails — саме тому все нижче працює без окремих трюків. Кожен рядок закріплений тестом.

ПоведінкаЯк саме
✓ Стектрейси Помилка всередині партіала показує його файл і рядок, бо Rails скомпілював шаблон із власним identifier. Сторінка помилки в development — звичайна, з підсвіченим рядком.
✓ locals і strict locals Партіали зі strict locals ідуть через Template#render, який володіє перевіркою аргументів і своїм повідомленням про помилку.
✓ Перезавантаження в dev Кеш вимикається, коли ActionView::Resolver.caching? хибний; плюс railtie чіпляє ViewBind.clear_cache до релоадера.
✓ Дайджести фрагментного кешу Власний DependencyTracker бачить рядки bind_render "…" і додає їх у залежності — інакше правка партіала не змінювала б ключ cache у батька. Він розширює вже зареєстрований трекер, а не підміняє його.
✓ Локалі та variants details_key — перший рівень ключа кешу.
! Інструментація view Подій render_partial.action_view для прив’язаних партіалів немає — це і є частина виграшу. APM перестане показувати їхній тайминг.

Три обмеження, про які варто знати одразу

Немає опцій :layout, :cached, :spacer_template — там, де вони потрібні, лишається render (їх можна змішувати в одному шаблоні). Трекер знаходить лише літеральні рядки, тож шлях, зібраний у рантаймі, невидимий для дайджестів. І партіал, який перепризначає @output_buffer і не повертає його, втратить свій вивід.

06Скільки це дає

Сторінка бенчмарку: 200 карток, вкладене дерево партіалів, 10 запитів у базу, однаковий HTML на всіх маршрутах. Медіани 5 запусків по 5 раундів.

Головний висновок для практики

Layout цілком — header, nav, flash, sidebar, footer, близько 60 викликів — дає 1.02×, тобто нічого. Весь виграш там, де партіал викликається по разу на рядок. Переписуйте цикли, а не обгортку.

І база даних вирішує, скільки з цього лишиться

Ті самі 10 запитів на PostgreSQL додають ≈7 мс кожному маршруту однаково, тож 2.57× перетворюються на 1.58×. Кількість об’єктів при цьому майже не змінюється (3.30× проти 2.98×) — тому саме її варто порівнювати між середовищами.

07Як побачити час рендерингу

Прив’язані партіали не кидають подій render_partial.action_view — це частина виграшу. Разом із подіями зникають і рядки Rendered … у логах: на сторінці бенчмарку їх стає 2 замість 65. Підсумковий час у Completed … (Views: 16.9ms) лишається на місці, губиться саме розбивка.

config/environments/development.rb
ViewBind.profile = true
Заміри: Rails 8.1.3.1, Ruby 3.4.5 з YJIT, production, SQLite (де не вказано інше). Кількість об’єктів точна; мілісекунди залежать від навантаження машини. Окремий документ про bind_render_memo — про те, коли має сенс кешувати саму розмітку.
