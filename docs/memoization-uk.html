Як працює bind_render_memo

Партіал рендериться один раз на кожен унікальний набір locals, а далі в буфер дописується збережена розмітка. Ключ кешу має чотири рівні — і кожен з них з’явився після конкретного бага.

кеш живе на view, вмирає з реквестом попадання ≈ 0.94 мкс рендер leaf-партіала ≈ 1.11 мкс 4 рівні ключа

01Що саме зберігається

Звичайний bind_render щоразу виконує скомпільований метод шаблону. bind_render_memo робить це лише перший раз: результат перехоплюється через capture і кладеться в хеш на самому об’єкті view. Кожен наступний виклик з тими самими locals просто дописує готовий рядок у буфер.

lib/view_bind/helper.rb — суть
if by_value.key?(key)
  html = by_value[key]              # попадання: партіал не виконується
else
  html = capture { bind_render(path, **locals) } || ActiveSupport::SafeBuffer.new
  by_value[key] = html if by_value.size < MEMO_LIMIT_PER_SHAPE
end

output_buffer << html
nil

02Ключ із чотирьох рівнів

Кеш — це вкладені хеші, а не один складений ключ. Так попадання не створює жодного проміжного об’єкта, окрім масиву імен locals, і не резолвить шаблон.

03Що станеться без details_key

Найсвіжіший баг. Партіал має варіант для телефона; сторінка міняє variant посеред рендеру. З details_key у ключі — все правильно, без нього — memo віддає розмітку, зроблену до перемикання.

04Три правила, без яких буде тихо неправильно

ПравилоЩо станеться, якщо порушити
1 Тільки прості значення Ключем стають лише String, Symbol, Numeric, true, false, nil. Модель як local — виклик автоматично падає у звичайний bind_render, бо два різні записи, що порівнюються як рівні, поділили б одну розмітку.
2 Жодних побічних ефектів На попаданні партіал не виконується, тому content_for, provide, лічильники та реєстрація ассетів спрацюють один раз. Партіал з content_for :counters, "x", відрендерений тричі, дає "xxx" через bind_render і "x" через memo — розмітка при цьому однакова.
3 Партіал має бути дорожчим за пошук Попадання коштує ≈0.94 мкс незалежно від вмісту партіала. На однотеговому партіалі (1.11 мкс) це дає 1.18× — тобто нічого. Реальний виграш починається там, де партіал важчий: цикл на 10 рядків — 8.5×, важке піддерево — 37×.

Що безпечно за замовчуванням

Кеш живе на об’єкті view і вмирає разом із реквестом. Тому партіал, який читає I18n.locale або current_user через хелпер, лишається коректним: у межах одного реквесту вони незмінні. Між реквестами нічого не переноситься.

05Скільки це дає насправді

Сторінка бенчмарку: 200 карток, 2 662 виклики рендеру, 10 запитів у базу. Memo увімкнено для одного піддерева, однакового для всіх карток.

Чесний підсумок

bind_render_memo економить 1 381 об’єкт і нуль часу на цій сторінці: 4.70 мс проти 4.67 мс — усередині розкиду між запусками. Це інструмент проти тиску на GC під навантаженням, а не спосіб зробити сторінку швидшою. Основний виграш дає bind_render, не memo.

Історія цього хелпера

Чотири раунди рев’ю, три баги з тихо неправильною розміткою — і всі три через те, що ключ робили коротшим заради швидкості: спершу зникли імена locals, потім details_key, а між ними memo взагалі не спрацьовував у development. bind_render і bind_render_each за той самий час не дали жодної знахідки. Якщо колись доведеться вибирати, що видалити — кандидат очевидний.

Заміри: Rails 8.1.3.1, Ruby 3.4.5 з YJIT, SQLite, production, медіани 5 запусків по 5 раундів з 20 повних реквестів. Кількість об’єктів точна й не залежить від навантаження машини; мілісекунди — залежать.
